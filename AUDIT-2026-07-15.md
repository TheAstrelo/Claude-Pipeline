**Date:** 2026-07-15 · **Scope:** full repo, 13 dimensions · **Method:** every claim below survived adversarial verification against the source. Refuted claims are excluded.

## The one sentence

**The pipeline has never executed a single phase — every one of the 17 `claude -p` invocations passes `--max-tokens`, which is not a Claude Code CLI flag, so every phase dies at argv parse — and the entire documentation set describes it as a working, measured system.**

Everything else in this report is downstream of that. `.claude/AGENTS.md:42` still reads `*Last updated: Never (no pipeline runs yet)*`. `history.json` reads `{"runs": [], "totalRuns": 0}`. `.claude/artifacts/` does not exist. Those are not stale files — they are the honest ones.

Proven by direct binary inspection and by execution:

```
grep 'max-tokens' <cli.js v2.1.50>          → 0 occurrences
env -u CLAUDECODE claude -p --max-tokens 1000  → error: unknown option '--max-tokens', exit 1
control: --effort low --max-budget-usd 0.01    → real model response
```

And a second, independent blocker sits behind it: `CLAUDECODE=1` is set inside the Bash tool, and `claude -p` refuses to launch nested. `grep -rn "CLAUDECODE"` across the repo → **zero hits**. It is never unset. So even with the flag fixed, the orchestrator — which *is* bash-in-markdown running inside a Claude Code session — cannot spawn its own children.

### The validators fight the prompts

This is the most elegant bug in the repo. **Phase 11 — the HARD security gate — instructs the model to emit the exact strings its own gate greps for.**

:2152  CONSTRAINT: "Severity markers are exactly CRITICAL/FAIL/PASS (no other words)"
:2164  VALIDATOR:  no_critical → ! grep "CRITICAL" $SESSION/qa-report.md   (HARD)

An obedient agent echoing the template fails the gate on a clean scan. `:2167 no_secrets → ! grep -i "Hardcoded"` fails on "Secrets: not hardcoded — CLEAR". **The inverse is worse and the audit nearly missed it:** an XSS or auth-bypass finding is `FAIL` severity and emits none of the four trigger tokens — so it **passes all five HARD gates green.** The gate measures vocabulary, not vulnerability, and it fails open on exactly the finding classes it exists to catch.

## Part 3 — Genuinely good

Credit where it's earned. There is real engineering here and it deserves to be named.

**The prompt skeleton is good, and consistently applied.** ROLE / CONSTRAINTS / CONTEXT / TASK / FORMAT / VERIFY across 17 inline prompts. The constraint text is frequently excellent — `:1298` *"no vague 'this could be better'"*, `:2131` *"False negatives (missing a real vulnerability) are far worse than false positives. When uncertain, flag [REVIEW_NEEDED] rather than marking safe."* That's real prompt engineering, not template-filling.

**The 12-phase decomposition is sound.** Pre-check-before-build is the highest-value idea in the repo and nobody else does it. The gate taxonomy (HARD/SOFT/NONE) is a good model. The Phase 3 three-critics-plus-aggregator topology is right in shape.

**The recovery loops in `run-pipeline.sh:860-895` are correctly designed.** Increment → revise → re-run the checking phase → test the verdict → break or loop, capped, then `pause_for_human`. That is a real feedback loop. It's killed by one `((retries++))`. The design was right; the bash was wrong.

**`.claude/rules/` is the actual moat.** The MUI Grid v2 syntax, the `do`-is-a-reserved-alias trap, the duplicate migration IDs, 200-205 being destructive — that is real, hard-won, un-inferable project knowledge. It is the one thing in this repo the harness cannot do for you. (It is also currently a liability, because it ships to strangers as authoritative. Same asset, wrong packaging.)

**`notify.sh` is the most portable script in the repo.** Correct `MINGW*|MSYS*|CYGWIN*` branch, beep + toast + `printf '\a'` fallback. It's the one that never runs.

**`detect-project.sh:66-136` already computes `TEST_COMMAND`** for npm/bun/pytest/go/cargo. The work is done and thrown away. `settings.json:89` sits at `"testCommand": null`.

**Hooks fire in `claude -p` children — proven.** I built a temp project and ran a real child session: `SessionStart`, `Stop`, `SessionEnd`, `PreToolUse(Bash)`, `PostToolUse(Bash)` all fired; `$CLAUDE_PROJECT_DIR` resolved. A `PreToolUse` returning `{"permissionDecision":"deny"}` **blocked** the command and the model reported the reason back. Since each phase *is* a child session, `Stop` fires per phase. **Your "notify per stage" ask is a settings.json entry, not orchestration work.** The subprocess-per-phase design — bad for caching — is accidentally perfect here.

**`targets/codex/codex-pipeline.sh` is better engineered than the Claude-native path.** `:25-26` sets defaults, `:48-49` exposes `--model-strong=` / `--model-fast=`. It also implements the Phase 6 retry loop the Claude target lacks. Your port is the reference implementation.

**Zero MCP is accidentally correct for caching.** MCP connect/disconnect is a documented cache-invalidation trigger and can fire with no user action. You avoid the whole class. (The cost is lost capability, not cache performance.)

**`--bare`, `--json-schema`, `--effort`, `--max-budget-usd`, `--max-turns` all exist and are all unused.** Every lever you need is already in the CLI you have installed.
